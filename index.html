Half-GFN: chasing giant primes on a machine you own

A small, self-contained toolchain for hunting a particular family of very large prime numbers — no cluster, no cloud, no account. Just your CPU, your GPU, and a lot of patience.

Hunting record-breaking primes is usually a team sport. Projects like GIMPS pool thousands of volunteer PCs to find the next biggest prime. This project asks a different question: how far can one person get, alone, on hardware that is already on their desk? No distributed client phoning home, nothing that stops working when a server goes dark — a toolchain you can clone, build, and run on a laptop, that keeps producing real, provable results.

It targets one specific, slightly exotic family of numbers, and it carries each candidate all the way from "might be prime" to a mathematical certificate that says "is prime, no doubt." Here is how the machine works.

1The quarry: "halved" generalized Fermat numbers

Every number the project tests has the same shape:

\[ M = \frac{b^{N} + 1}{2}, \qquad N = 2^{k}, \quad b \text{ odd} \] e.g. \(b = 3,\ k = 4 \Rightarrow N = 16 \Rightarrow (3^{16} + 1)/2 = 21\,523\,361\) (prime)

Unpack that in plain words. Take an odd number \(b\), raise it to a power that is itself a power of two (that is what \(N = 2^{k}\) means — 2, 4, 8, 16, 32 …), add one, and halve the result. Because \(b\) is odd, \(b^{N}+1\) is even, so the halving always comes out whole.

Numbers of the form \(b^{N}+1\) with a power-of-two exponent are called generalized Fermat numbers, a classic happy hunting ground for large primes. The twist here is the division by two — hence "half-GFN." That small change rules out the usual quick primality test for Fermat numbers, which is exactly what makes this family a fun, slightly off-the-beaten-path target to build your own tools for.

Why these at all? Because the exponent being a power of two gives the numbers a very regular internal structure — and that structure is precisely what lets a clever sieve and a fast multiplication trick (both below) chew through candidates that are otherwise far too big to test by brute force. Crank \(k\) up and the numbers balloon fast: \(k = 10\) already means roughly 3 000 decimal digits, \(k = 16\) around 200 000 digits.

2The assembly line

You cannot just ask "is this 200 000-digit number prime?" and wait. The work is staged, cheapest filter first, so that expensive tests only ever see candidates worth the effort.

Stage 1 · Sieve

Throw out the easy losers

Like the ancient Sieve of Eratosthenes, but smart: any small factor of one of these numbers must have a special form, so the sieve only ever tries those. Most candidates fall here, fast.

Stage 2 · PRP

Ask: "probably prime?"

A fast probabilistic test (Miller–Rabin) that survivors must pass. A pass means "almost certainly prime"; a fail is a definite "composite." Cheap enough to run on everything the sieve lets through.

Stage 3 · Proof

Turn "probably" into "certainly"

The survivors get a real primality proof (APR-CL / ECPP, via PARI/GP) that produces a certificate. Only now is a number allowed to be called prime.

The distinction in stage 2 matters more than it looks. A "probable prime" has passed a test that every prime passes — but a vanishingly small number of composites sneak through too. During development the tools actually caught one such impostor: a number that happily passed the test for one base yet was composite. That is not a bug, it is the whole reason stage 3 exists. Nothing here is called prime on a probabilistic nod alone.

3Making it fast — and then much faster

The project started as a readable Python script, got rewritten in C++ for speed, and then learned to use every core and, eventually, the graphics card. The interesting part is why a GPU helps at all.

The expensive thing a primality test does, over and over, is square a gigantic number — hundreds of thousands of times per candidate. Multiply two million-digit numbers the way you learned in school and the work grows with the square of the length: hopeless. The standard escape is an FFT — the same Fast Fourier Transform used in audio and image processing — which turns multiplication into something that grows almost linearly instead. Suddenly multiplying million-digit numbers is merely slow, not impossible.

And an FFT is exactly the kind of wide, repetitive arithmetic a GPU devours. So the heavy multiplication gets handed to the graphics card — using an integer variant of the transform (an NTT), which is exact to the last bit, no rounding to worry about. On an NVIDIA RTX 4060 the GPU engine overtakes a CPU core at \(k = 15\); on an Apple M2 Pro, one step later at \(k = 16\), and it keeps pulling ahead as the numbers grow:

A reality check that surprised us: when the GPU engine was first working it was slower than the CPU — and profiling showed the graphics card was not the problem at all. Almost all the time was being burned in a bookkeeping step back on the CPU. Measuring, not guessing, is what found the real bottleneck and flipped the result. A good reminder that intuition about where a program spends its time is usually wrong.

4Trust nothing, verify everything

When you are generating numbers no one has ever checked, "it ran without crashing" is not good enough. So every fast path is pinned to a slow, trusted one. The GPU's answer is checked against the CPU's answer; both are checked against a rock-solid reference library (GMP). A hand-written test runs millions of operations and compares every single bit.

The guiding rule throughout: never ship a result you cannot independently reproduce, and never merge code to the main branch until it has actually been shown to work on the target machine. For a prime hunt that may run for days, a silent hardware glitch or an off-by-one is the enemy — the cross-checks are the project's immune system.

Run solo on ordinary hardware, the pipeline has already turned out a healthy pile of proven primes (not just probable ones):

The larger the exponent \(k\), the rarer and the more expensive the primes become — and that is where the GPU work earns its keep, and where the next experiments are headed.
